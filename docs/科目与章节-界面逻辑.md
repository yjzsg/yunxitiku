# 科目与章节 · 界面逻辑梳理

> 行号基于 2026-10-09 的 `main`（`99820f3`）。
> 本文由读代码产出，**未做真机验证** —— 涉及 UI 行为的结论请以实测为准。

## 1. 一句话总览

科目只有一个角色：**决定 `courseId`**。
章节列表以**扁平数组**返回，前端现场拼成树、**只存在内存**。
两块靠 `state.currentCourse` / `state.currentChapter` 粘合：前者变就重拉章节，
后者变就把「本节点 + 全部子孙」的 id 塞进 `/api/questions`，**题目过滤全在 SQL 里**。

```
科目面板（点科目名 / 点「考试题库」）        app.js:1687, 9033
 └─ selectCourse                            app.js:1726
     ├─ loadChapters                        app.js:1780   GET /api/chapters?courseId=  ← 扁平
     │    └─ renderChapters 1792 → buildChapterTree 1822（建树）
     │                           → buildChapterDoneIndex 1908（(已做/总数)）
     ├─ loadTypes                           app.js:2000
     └─ loadQuestions                       app.js:2030
          → rememberQuestionChapters        app.js:2093
          → backfillQuestionChapters        app.js:2095（异步）
章节项点击 → selectChapter                  app.js:1979
```

## 2. 数据模型

| 实体 | 表 | 关键列 |
|---|---|---|
| 科目 | `course` | `icourseid`(PK)、`ccoursename`、`ihadbuy`、`bstopflag`、三个变更日期 |
| 章节 | `coursechapter` | `ichapterid`(PK)、`icourseid`、`cchaptername`、`cchaptercode`、`igrade`、`itype` |
| 题目 | `coursesubject` | `isubjectid`(PK)、`icourseid`、`ichapterid`、`isubjecttype`、`iindex` |

一题**只挂一个** `ichapterid`。另有外挂映射 `subjectId → 课本章名数组`（一题多章），
由 `ChapterMapStore` 生成、落 `data/chapter-map.json`、走 `GET /api/chapter-map`。

**`igrade` / `itype` 的语义**（前端 `app.js:624-630`，后端 `Program.cs:4144-4161`）：

| 列 | 含义 |
|---|---|
| `igrade` | 层级深度：0 = 卷册/系列，1 = 章或「整卷」，2 = 节 |
| `itype` | 卷册系列大类，**父/子判定必须同 itype** |
| `cchaptercode` | 层级路径码，子 code 以父 code 为前缀；`length = (igrade+1)*2` |

⚠️ **树不是后端给的** —— `/api/chapters` 返回 JSON 数组，每项只有
`{id,name,code,grade,type,questionCount}`，**没有 children**。

## 3. 流程一：进入应用 → 选科目 → 加载章节

```
init (app.js:1199)
 └─ enterApp (1311)
     ├─ loadUserData      1382  /api/user/load
     ├─ loadCourses       1655  /api/courses
     ├─ loadChapterMap    1330  /api/chapter-map
     └─ restoreLastCourse 1666
         ├─ 只在 courseId 真的变了才清 analysis*/exam* 章节状态  1731-1737
         ├─ currentCourse = course (1739)、currentChapter = null (1752)
         ├─ loadChapters() (1764)
         ├─ 恢复 lastChapterId → currentChapter (1766-1769)
         └─ loadTypes (1771) → loadQuestions (1773)
```

**建树时机（关键）**：`renderChapters` 第 3 行就建树（`1796-1801`），
因为 `state.chapters` 是扁平的，直接拿它递归会炸：

```
1799  const roots = buildChapterTree(state.chapters)
1800  state.chapterTreeRoots = roots
1801  state.chapterDoneIndex = buildChapterDoneIndex(roots, courseStore)
1805  allTotal = Σ chapterTotalCount(root)      ← 必须建树后才能递归
```

父节点判定（`1826-1838`）：同 `type`、`grade` 差 1、父 `code` 是子 `code` 前缀，
多候选取 **code 最长**者；找不到父的进 `roots`。

**科目入口有 3 条路径**，全部汇到 `selectCourse`：

| 断点 | 入口 |
|---|---|
| ≥761px | 内容区科目名 `#courseTitle` |
| ≤760px | 顶栏科目名 `#navCourseTitle` |
| 任意 | 点当前模式项「考试题库」（**无 UI 提示的隐藏交互**）`app.js:9033` |

前两个绑的是同一个函数 `app.js:9140-9141`，`setCoursePicker` 会同步两处的 `aria-expanded`。
`#coursePickerBtn` 已从 HTML/CSS/JS 全部删除。

## 4. 流程二：选章节 → 过滤题目

**后端查询，不是前端过滤。**

```
selectChapter(chapter)  app.js:1979
 ├─ 取消在途请求（三个 token 自增）  1980-1984
 ├─ currentChapter = chapter；currentIndex = -1  1986-1987
 ├─ storage.profile.lastChapterId = chapter.id | 0  1990
 └─ renderChapters (1991) → loadTypes (1992) → loadQuestions (1994)
```

参数组装（`app.js:716-721` + `590-602`）：

```
ids = selectedChapterIds(currentChapter) = {id} ∪ 递归全部子孙
ids.length === 1 → chapterId=<id>
否则              → chapterIds=<a,b,c…>
```

后端 `Program.cs:3235-3265`：`where s.icourseid=@courseId and coalesce(s.bstopflag,0)=0`，
再按 `chapterId` / `chapterIds in (…)` 过滤。

**父节点选中 ⇒ 整棵子树进 SQL**，没有「半选」概念。`currentChapter === null` 即「全部章节」。

## 5. 流程三：章节进度 (n/m)

**m（总数）**：`chapterTotalCount(node)` = 自身 `questionCount` + 递归子节点之和（`1865-1867`）。
`questionCount` 是后端**相关子查询实算**（`Program.cs:3195`），不是 `coursechapter.icount`
（实测 `icount` 是脏数据）。

**n（已做）**：`state.chapterDoneIndex`（`1908-1926`）

```
courseStore.done = { qid: true }              ← 答题时写
courseStore.questionChapter = { qid: cid }    ← qid → chapterId 映射
   ├─ 来源 A  rememberQuestionChapters  1873-1884  （/api/questions 每项都带 chapterId）
   └─ 来源 B  backfillQuestionChapters  1892-1904  （GET /api/question-chapters 全课程 pairs）
buildChapterDoneIndex 1908-1926
   按映射归到章（1912-1916）→ 从根递归累加（1918-1923）
渲染：(${chapterDone}/${chapterTotalCount(chapter)})  1965-1966
```

**父章已做数确实累计子节**（`walk`）。但「全部章节」是**另一套口径**：
`allDone = Object.keys(courseStore.done).length`（`1806`）。

**回填开关的 4 个盲区**：`backfillQuestionChapters` 全代码**只有 1 个调用点**
（`loadQuestions` 的 `2095`），而 `loadQuestions` 在那之前有 4 处早退：

| 早退 | 位置 |
|---|---|
| `mode === "training"`（**默认模式**） | `2034-2043` |
| `mode === "progress"` | `2044-2054` |
| `mode === "exam"` 且考试进行中 | `2056-2059` |
| 模式 id 过滤后为空 | `2078-2084` |

模拟考场完全绕过这条链路（自己拉题，不调这两个函数）。

## 6. 状态与存储

| 载体 | 内容 | 生命周期 |
|---|---|---|
| `localStorage` | 主题、session user/token、last user | 主题仅本机 |
| 内存 `state` | `chapters`(扁平)、`chapterTreeRoots`、`chapterTreeIndex`、`chapterDoneIndex`、`expandedChapters`、`chapterMap`、`currentCourse/currentChapter` | **刷新即丢** |
| `userdata/<user>.json` | 整个 `state.storage`：`profile.lastCourseId/lastChapterId`、`courses[cid] = {answers,done,correct,wrong,verified,questionChapter,questionChapterFilled}`、`wrong`、`tags`… | 450ms 防抖 → `POST /api/user/save`，带 `If-Match` revision |
| `data/chapter-map.json` | `subjectId → 课本章名数组` | 进应用拉一次；题库更新后由后端重建 |

**没有任何地方把章节树写进 localStorage** —— 每次进入都重新拉 + 重新建树。

切科目时清掉的：`currentChapter`(1752)、`currentIndex/answers/submitted`(1753-1756)、
`analysis*`(1732-1733)、`exam*`(1734-1736)、`smartPractice`(1746-1749)、`expandedChapters`(1787-1788)。
**没清**：`chapterTreeRoots / chapterTreeIndex / chapterDoneIndex / state.chapters`（见问题 2）。

## 8. 发现的问题

### 高

**1. 默认落地模式下 qid→chapterId 映射永不建立 → 章节 (已做) 恒为 0**

`loadQuestions` 在 `mode === "training"` 时于 **`app.js:2034-2043` 提前 return**，
而 `rememberQuestionChapters` / `backfillQuestionChapters` 的唯一调用点在其后（`2093` / `2095`）。
默认模式就是 training（`app.js:2`、`1326` 无 `lastMode` 时回落）。

**后果**：新账号或回落到训练页的用户，章节树每行显示 `(0/m)`，且**无限期**保持 0。

**讽刺的是**：此时 `ensureAnalysisQuestionsInBackground`(`2040`) 已经用 `limit=30000`
把整门课的题（含 `chapterId`）拉下来了（`2143-2154`），**却没喂给 `rememberQuestionChapters`**。

*修复方向*：`loadAnalysisQuestions` 拿到 items 后顺手 `rememberQuestionChapters(items)`；
或在 `selectCourse` 里对当前课程无条件调一次 `backfillQuestionChapters`。

### 中

**2. 切科目时章节树三件套不清空，请求失败会留下「新科目 + 旧章节」的错配**

`selectCourse` 不重置 `state.chapters/chapterTreeRoots/chapterTreeIndex/chapterDoneIndex`
（`1726-1778`），而 `currentCourse`(1739) 和标题(1760) **先**改。
`loadChapters` 没有 try/catch（`1780-1790`）。

`/api/chapters` 一旦失败（401/403/网络），流程在 `1764` 中断：
界面显示**新科目名 + 旧科目的章节列表**；点旧章节 → 送出旧 `chapterId` + 新 `courseId` → 空题单。

**3. `questionChapter` 映射跟着用户数据整包保存，量级远超设计假设**

映射存在 `state.storage.courses[cid].questionChapter`，而保存是「整个 `state.storage` POST 一次」。
实测单门课 11815 题的映射 JSON = **211 KB**（`app.js:1872` 的注释按「几十 KB」估算 ✗）。
每访问一门课就再叠一份，直接放大每次答题的请求体和 409 冲突的回滚成本。

**4. 「全部章节」与各章的已做数口径不一致**

`allDone = Object.keys(courseStore.done).length`（不过滤映射、不减已删题），
各章的 n 只统计能在映射里找到 chapterId 的题。映射未建成时（问题 1）两者天差地别；
题库更新删题后 `done` 不清理，可能显示 `已做 > 总数`。

**5. 模拟考场章节树：取消子章无效**

勾选只向**下**传播（`911-916`），没有向上更新、无半选态。
收集时 `normalizeExamChapterIds`(`838-848`) 会**剔除祖先已被选中的子项**（`768-770`），
于是「父勾、子取消」= 父 id 仍进卷，`fetchExamPartQuestions` 又展开整棵子树 →
**用户取消了的子章，卷子里照样出题**。默认是**全选**（`859-865`），所以这是常态化的第一次交互。

### 低

**6.** 恢复上次章节时不展开祖先链 —— `ensureChapterExpansion` 只自动展开 `roots[0]`（`1848-1852`），
被恢复的章节若在折叠分支下，`.chapter-row.active` 在屏幕外。

**7.** 题库更新后残留旧章节上下文 —— `8702-8705` 清了 `chapters/types/questions`，
但没清 `chapterTreeRoots/chapterTreeIndex/chapterDoneIndex/currentChapter`
（管理员上传路径 `7374-7378` 是清了的）→ `updatePickerHint` 仍显示旧章节名。

**8.** 顶栏「刷新列表」按钮不刷新章节 —— 只 `loadCourses()`（`9209`），不重发 `/api/chapters`。

**9.** 父级判定对 `igrade` 连续性有硬依赖、无兜底 —— 上游若 grade 跳级，
子节点会**静默变成根节点**：计数仍对，但层级/缩进错乱，`selectedChapterIds` 不再包含它。

**10.** 前后端 code 前缀比较语义不一致，注释却声称一致 ——
`Program.cs:4144-4146` 写「必须和前端逐字一致」，但前端 `startsWith` 大小写敏感（`app.js:1833`），
后端两处是 `OrdinalIgnoreCase`（`3606` / `4158`）。纯数字 code 下无影响，属**潜伏**。

**11.** `/api/chapters` 取了 `ch.icount` 却不用，而 `icount` 实测是脏数据 ——
SQL 选了（`3194`）但投影用的是实算子查询（`3207`）。
实测 323 处 `icount` 与实时题数不一致。**目前正确**，但若有人「顺手」改成读 `icount`，全站总数立刻错。

### 后端：courseId 非法与重复行

| 情形 | 结果 |
|---|---|
| 缺参 / 非整数 | **400**（框架模型绑定失败，无自定义 body） |
| 整数但不存在 / 0 / 负数 | **200 + `[]`**（**无存在性校验**，也不查 `courseId > 0`） |
| 整数但该用户未被分配 | **403** `{ok:false,error:"未分配该题库"}` |
| DB 抛异常 | **500** `{ok:false,error:"服务器内部错误…"}` |

**重复行：不会扇出** —— `GetChapters` 是单表 + 相关子查询；`GetQuestions`/`GetCourses`
的 JOIN 全部打在主键上。实测 Σ(每章实算题数) 与课程题数逐门相等。

**一个跨表隐患**：`GetQuestionChapterPairs`（`3293-3296`）不 JOIN `coursechapter`、
不校验章节是否停用。当前 0 条孤儿题，但上游若出现指向停用/不存在章节的题，
前端会计进 `direct` 而树上没有这一行 → 与问题 4 同样的差额。
